## 三、系统架构演进历程

```
v0.9  单体 FastAPI + SQLite + Vue3 CDN 单页
        │   分层：routers / services / utils，前后端分离
v1.0  ├─ 前端信息架构重构（5 主菜单 + 合并页 + 独立抽奖）
        │   建立 docs/ 文档体系，架构决策文档化
v1.1  ├─ 管理后台可视化层（Chart.js 引入，富统计接口聚合）
v1.2  ├─ 安全层强化（速率限制、Token 机制审计、日志脱敏）
v1.3  └─ 外部集成层 + 数据治理
            ├─ webhook_push_service：异步线程推送，主流程零阻塞
            ├─ dingtalk_bot_service：Outgoing 回调双向消息（HMAC 验签）
            ├─ site 配置层：单行配置表模式（SiteConfig/PushConfig）
            ├─ 时区治理：全链路 naive 北京时间（utils/timeutil）
            └─ Alembic 迁移链：001 → 002(推送) → 003(时区) → 004(标语)
```

关键演进决策：

- **单行配置表模式**：PushConfig、SiteConfig 均采用「单行表 + get_or_create 惰性建行 + PUT 全量保存」，后台配置即改即生效，无需重启。
- **异步推送与主流程解耦**：推送在 daemon 线程执行，任何异常只写 PushLog，绝不影响打卡主链路。
- **时区统一为 naive 北京时间**：`now_local()` 显式 +8 不依赖容器 TZ，同时 Dockerfile 设 `TZ=Asia/Shanghai` 双保险；统一 naive 规避 offset-naive/aware 混比错误。
- **迁移优先于重建**：历史数据一律走 Alembic 平移/补列（如 003 对 11 张表时间戳整体 +8h 并重算打卡归属日期），保证升级零数据丢失。

## 四、关键技术实现要点

| 模块 | 技术要点 |
| --- | --- |
| 防代打卡 | 照片真实性/尺寸校验 + 地理位置距离阈值 + insightface 人脸 1:1 比对（无网自动降级安全模式）+ 场景综合判定 |
| 连续打卡统计 | `recompute_and_grant` 基于有效打卡日期集合重算当前/最长连续，7 天自动 +1 抽奖资格 |
| 转盘抽奖 | 后端加权随机 + 前端 `conic-gradient` 转盘、5 圈精准落点动画（落点角度与后端结果逆向对齐） |
| Webhook 推送 | URL 前缀白名单（仅钉钉/企微官方域名，防 SSRF）、事件类型过滤、滑动窗口限频、PushLog 不落 URL |
| 钉钉双向机器人 | 加签验签 `HMAC-SHA256(timestamp+"\n"+token)`，支持统计/待审核/查询/群内审核指令，审核复用 `checkin_service` 同一逻辑 |
| 时区治理 | `datetime(col,'+8 hours')` SQL 整体平移历史数据；`check_date=date(check_time)` 重算跨日归属；升降级双向可逆 |
| 站点动态配置 | 公开 `GET /api/site-config`（登录前可用，服务端兜底默认值）+ 管理端 PUT（长度校验、置空恢复默认）；前端 `cache:"no-store"` 刷新即生效 |
| 增量部署 | `scripts/deploy.sh local|prod`：部署前自动备份数据库 → 重建镜像（保留数据卷）→ 启动自动执行 Alembic 迁移 → 健康检查 |

## 五、遇到的主要挑战及解决方案

| 挑战 | 解决方案 |
| --- | --- |
| 「服务器时间不对」实为三层问题（宿主机时钟 / 容器 TZ=UTC / 应用显式存 UTC） | 分层定位：宿主机 NTP 正常无需处理；容器加 `TZ=Asia/Shanghai`；应用层新建 `timeutil.now_local()` 统一替换 22 处写库点；历史数据用迁移 003 整体平移 +8h，生产 13 条打卡零丢失 |
| 早上 8 点前打卡被记到前一天 | 根因是容器 UTC 下 `date.today()` 偏差；修复后 `check_date` 由北京时间判定，并对历史记录 `date(check_time)` 重算 |
| naive/aware datetime 混比 TypeError 风险 | 全链路统一 naive 北京时间；`challenge_service._make_aware` 改为 `_make_naive`（顺带修复 unlock_at 与 UTC now 比较的 8 小时隐藏偏差） |
| 推送故障不能影响打卡主流程 | daemon 线程异步执行 + 独立 DB 会话 + 异常仅记 PushLog |
| Webhook 配置错误/恶意 URL 的 SSRF 风险 | 仅允许钉钉/企微官方 API 前缀，其余一律拒绝保存 |
| 人脸识别在无外网沙箱不可用 | 启动时探测模型可用性，不可用自动降级安全模式（跳过人脸、保留其余三重校验），部署环境联网即自动生效 |
| 部署脚本健康检查窗口过短导致误报失败 | 迁移+启动实际约 15s，超过脚本 10s 阈值；建立「脚本报错 → 人工复核容器状态/迁移日志/health」的标准复核流程 |
| 敏感信息险入仓库 | 全库清理 + 根 `.gitignore` 门禁（密钥/数据库/上传/备份/日志全类目拦截）+ 提交前逐文件扫描 + 安全扫描门禁 |

## 八、部署上线情况

| 环境 | 方式 | 状态 |
| --- | --- | --- |
| 本地测试环境 | Docker Compose（`scripts/deploy.sh local`），数据卷持久化 | ✅ 运行中，v1.3 |
| 生产环境 | SSH 增量部署（`scripts/deploy.sh prod`），部署前自动备份数据库 | ✅ 运行中，v1.3 |

部署要点：

- 每次部署自动备份 SQLite 至备份目录（本地 `.backups/local/`、生产 `data/backups/`），保留可回滚快照。
- 容器启动时自动执行 Alembic 迁移，数据卷与代码分离，重建镜像不触碰数据。
- 中断窗口约 30s（停旧容器→起新容器），部署后按验收清单人工复核。
- CORS 白名单通过环境变量 `DEPLOY_ALLOWED_ORIGINS` 注入，不硬编码入库。

## 九、性能优化措施

- 推送异步化：Webhook 推送在 daemon 线程执行，打卡接口响应不受外部网络影响。
- 静态资源版本号（`?v=YYYYMMDD`）强制客户端缓存刷新，避免发版后旧脚本残留。
- 学生端页面合并与预加载：打卡/闯关合并页进入时预加载、子 tab 切换不重复请求。
- 配置接口 `cache:"no-store"` 保证配置实时生效的同时，其余静态资源仍走缓存。
- Docker 分层构建缓存：增量部署仅重建变更层，构建时间显著缩短。

## 十、安全加固实施情况

- **认证**：bcrypt 密码哈希 + 签名 Token；登录/注册速率限制（防暴力破解）。
- **接口权限**：公开接口最小暴露（site-config 只读展示字段），管理接口 `require_role("admin")`。
- **SSRF 防护**：Webhook URL 仅允许钉钉/企微官方前缀。
- **回调验签**：钉钉 Outgoing 优先加签模式（HMAC-SHA256），未配置 Token 拒绝服务。
- **日志脱敏**：PushLog 不记录 Webhook URL；部署脚本输出对密码打码。
- **仓库卫生**：数据库/上传照片/备份/密钥/环境变量全类目 `.gitignore` 拦截；历史敏感信息已全库清理；提交前执行安全扫描门禁。
- **输入校验**：所有配置项服务端长度/格式校验（如标题 ≤64 字、标语 ≤128 字）。

## 十二、代码质量提升

- 分层清晰：routers（协议层）/ services（业务层）/ utils（工具层），业务逻辑不散落在路由中。
- 复用优先：群内审核复用 `checkin_service.approve/reject`；标语功能完全复用标题的表/接口/前端加载函数。
- 时间处理收敛为单一入口 `utils/timeutil.now_local()`，消除 12 处模型默认值 + 22 处写库点的分散 `datetime.now` 调用。
- 迁移脚本防御式编写（表/列存在性检查、双向可逆），可在任意历史版本库上安全执行。
- 文档随代码同步演进（本目录 7 份文档 + 根 README），每版本更新 CHANGELOG。
