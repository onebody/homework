## 简介
本技术文档围绕"暑假作业打卡"系统中的"人脸识别（1:1 本人比对）"能力，系统化阐述以下要点：
- InsightFace 框架集成方案与模型加载策略
- 人脸底图采集流程（注册、特征提取、存储机制）
- **升级** AES-GCM认证加密机制确保人脸特征数据的静态安全保护和完整性验证
- 1:1 身份比对的算法实现、相似度阈值与置信度判断
- 异常情况处理：多个人脸检测、无人脸检测、人脸不匹配、服务不可用等
- 人脸服务可用性检查与降级策略，确保 AI 不可用时系统稳定
- 图像预处理规范、质量评估标准与性能优化建议
- 完整的错误码与调试指南，帮助快速定位问题

## 项目结构
本项目采用 FastAPI + SQLAlchemy 的轻量后端架构。人脸识别相关代码主要分布在路由层、服务层、工具层与配置层：
- 路由层：提供人脸采集、状态查询、撤销等接口；在打卡流程中调用验证服务
- 服务层：封装 InsightFace 模型加载、特征提取、1:1 比对、健康检查
- **升级** 安全加密层：负责人脸特征的AES-GCM认证加密和解密操作，支持向后兼容
- 工具层：图片基础校验、文件存储与 URL 生成
- 配置层：阈值、尺寸、模型名、模式开关、加密配置等
- 数据模型：用户表包含人脸字段，打卡记录表包含人脸结果字段

## 核心组件
- 人脸服务（face_service.py）
  - 懒加载 InsightFace FaceAnalysis 模型（buffalo_l），线程安全初始化
  - 特征提取：基于 OpenCV 解码图像，检测最大人脸并输出 512 维 embedding
  - **升级** 认证加密存储：使用AES-GCM算法对人脸特征进行认证加密后存储
  - 1:1 比对：余弦相似度计算，阈值比较判定 match/mismatch
  - 健康检查：is_available() 暴露服务可用性
- 路由层（face.py）
  - POST /api/face/enroll：采集人脸底图（要求仅一张人脸）
  - GET /api/face/status：查询当前用户是否已采集
  - DELETE /api/face/enroll：撤销人脸底图（解绑，保留历史文件）
- 综合验证服务（verification_service.py）
  - 将人脸 1:1 比对纳入打卡整体校验流程，返回结构化结果
- 打卡服务（checkin_service.py）
  - 在创建打卡时调用综合验证，依据人脸状态执行拦截或降级策略
- **升级** 安全加密模块
  - AES-GCM认证加密：提供对称加密算法保护人脸特征数据，同时验证数据完整性
  - 向后兼容解密：支持旧版本AES-CTR格式数据的解密操作
  - 密钥管理：安全的密钥生成、存储和轮换机制
  - 认证标签：确保加密数据的完整性和防篡改能力
- 工具层（image.py, storage.py）
  - 轻量图像解析（JPEG/PNG 尺寸与格式校验）
  - 上传文件持久化与公开 URL 生成
- 配置（config.py）
  - 相似度阈值、检测输入尺寸、模型名称、人脸模式（enforce/soft）
  - **升级** 加密配置：AES密钥、盐值、GCM模式参数、认证标签长度等安全参数
- 数据模型（models.py）
  - User 表含 face_enrolled、face_embedding、face_id_path
  - CheckIn 表含 face_status、face_score、face_flag 等字段

## 详细组件分析

### 人脸服务（face_service.py）
- 模型懒加载与线程安全
  - 使用全局锁保证首次加载只执行一次
  - 通过环境变量控制模型名称、检测尺寸、相似度阈值
- 特征提取（_embed）
  - 使用 OpenCV 解码字节流为图像矩阵
  - 调用 FaceAnalysis.get 获取人脸列表，按面积排序取最大人脸
  - 返回 embedding、人脸数量、提示信息
- **升级** 认证加密存储（_encrypt_embedding）
  - 使用AES-GCM算法对512维人脸特征向量进行认证加密
  - 生成随机nonce（初始计数值）确保相同明文产生不同密文
  - 生成认证标签用于验证数据完整性
  - 将加密数据、nonce和认证标签一起存储到数据库
- 注册（enroll）
  - 要求检测到且仅检测到一张人脸
  - 保存原始照片与认证加密后的embedding到数据库
- 1:1 比对（verify）
  - 读取用户已存认证加密embedding并解密（支持向后兼容）
  - 计算余弦相似度与阈值比较得到 match/mismatch
  - 返回结构化结果（status、score、message 等）
- 健康检查（is_available）
  - 用于外部监控或前端提示

## 安全加密机制

### AES-GCM认证加密实现
系统已从AES-CTR升级到cryptography库的AES-GCM认证加密算法，提供更强的数据完整性和防篡改保护。

**升级特性**
- **认证加密**：AES-GCM同时提供机密性和完整性保护
- **认证标签**：自动生成16字节认证标签验证数据未被篡改
- **Nonce管理**：使用随机nonce确保相同明文产生不同密文
- **向后兼容**：自动检测并支持旧版AES-CTR格式数据解密

**新加密流程**
1. **密钥派生**：使用主密钥和盐值派生AES-GCM密钥
2. **Nonce生成**：为每次加密生成唯一的12字节nonce
3. **数据加密**：对512维人脸特征向量进行AES-GCM加密
4. **标签生成**：自动生成认证标签验证数据完整性
5. **数据存储**：将加密数据、nonce和认证标签组合存储

**向后兼容解密流程**
1. **格式检测**：自动识别数据格式（GCM或CTR）
2. **GCM解密**：验证认证标签并解密新格式数据
3. **CTR兼容**：对旧格式数据进行传统解密
4. **特征比对**：使用解密后的原始特征进行相似度计算

### 安全配置管理
系统通过配置文件管理所有加密相关的参数：

- **FACE_ENCRYPTION_KEY**：AES-GCM加密主密钥，应存储在安全的位置
- **FACE_ENCRYPTION_SALT**：用于密钥派生的盐值
- **FACE_ENCRYPTION_MODE**：加密模式（默认使用GCM模式）
- **FACE_ENCRYPTION_NONCE_LENGTH**：Nonce长度（通常12字节）
- **FACE_ENCRYPTION_TAG_LENGTH**：认证标签长度（通常16字节）
- **BACKWARD_COMPATIBLE_DECRYPT**：启用向后兼容解密功能

### 密钥管理策略
- **密钥存储**：使用环境变量或安全配置管理服务存储密钥
- **密钥轮换**：支持定期更换加密密钥
- **向后兼容**：自动检测数据格式并选择相应解密方法
- **完整性验证**：GCM模式自动验证数据完整性，防止篡改攻击

## 性能与优化建议
- 模型加载
  - 懒加载与单例缓存避免重复初始化开销
  - 强制 CPU 运行（ctx_id=-1）提升部署稳定性
- 检测尺寸
  - FACE_DET_SIZE 越小越快但易漏检，建议根据设备性能调优
- 并发安全
  - 使用全局锁保护模型实例与检测过程，避免竞态条件
- **升级** 加密性能优化
  - AES-GCM硬件加速：利用CPU的AES-NI指令集提升加密性能
  - 内存池复用：重用加密上下文减少对象创建开销
  - 批量处理：支持批量加密请求提高吞吐量
  - 异步操作：非阻塞加密操作避免影响主流程
- 向量存储
  - 512 维向量以JSON文本存储，注意序列化/反序列化开销
  - **升级** 认证数据压缩：对加密后的数据进行压缩存储，减少存储空间
- 图像预处理
  - 轻量解析减少第三方库依赖，降低内存占用
- 降级策略
  - 模型不可用时返回明确状态，结合 enforce/soft 模式保障业务连续性
  - **升级** 加密降级：认证失败时可选择回退到兼容模式或记录详细错误信息

## 故障排查指南
- 常见问题
  - 未检测到人脸：检查拍摄角度、光线、遮挡情况
  - 多张人脸：引导用户单独拍摄本人正脸
  - 人脸不匹配：确认是否为同一人，调整阈值或重新采集
  - 模型不可用：检查 insightface 安装与网络下载，必要时切换 soft 模式
  - **升级** 认证失败：检查cryptography库安装、密钥配置、数据完整性
  - **升级** 向后兼容问题：确认旧格式数据格式正确，nonce和标签完整
- 日志与诊断
  - 查看人脸状态字段 face_status、face_score、face_flag
  - 关注综合验证返回的 scene_check 与 risk 等级
  - **升级** 加密日志：记录加密/解密操作的详细信息，包括认证标签验证结果
- 回退与降级
  - enforce 模式下模型不可用会返回 503，提示稍后重试
  - soft 模式下允许记录待审核，人工复核后再决定是否有效
  - **升级** 加密降级：认证失败时可尝试兼容解密模式，或记录详细错误信息供后续处理

## 结论
本系统通过 InsightFace 预训练模型实现了稳定的 1:1 人脸比对能力，并与打卡流程深度集成。**升级的AES-GCM认证加密机制**不仅确保了人脸特征数据在静态存储时的安全性，还提供了强大的数据完整性保护和防篡改能力。通过严格的图像质量校验、多维度风险判定、明确的降级策略和增强的加密保护，系统在 AI 服务不可用时仍能保持可控与可审计。向后兼容性设计确保了平滑的数据迁移，未来可扩展至 1:N 检索，只需扩展比对逻辑而不改动主流程。

## 附录：错误码与状态定义
- 人脸状态（face_status）
  - match：比对通过
  - mismatch：比对不通过
  - no_face：未检测到人脸
  - multiple_faces：检测到多张人脸
  - not_enrolled：尚未采集人脸底图
  - model_unavailable：人脸识别服务暂不可用
  - **升级** encryption_error：加密/解密操作失败
  - **新增** authentication_failed：认证标签验证失败（数据可能被篡改）
- 人脸标志（face_flag）
  - True：代打卡高风险（mismatch/multiple_faces/no_face）
  - False：低风险或未触发
- 场景检查（scene_check）
  - pass：正常
  - warn：存在风险需关注
- 风险等级（risk）
  - low：低风险
  - medium：中等风险
  - high：高风险
- HTTP 状态码
  - 400：请求参数或图像质量不符合要求
  - 403：权限不足（非学生操作）
  - 503：人脸识别服务不可用（enforce 模式）
  - **升级** 500：内部服务器错误（包括加密失败）
  - **新增** 422：数据完整性验证失败（认证标签不匹配）
