## 一、项目概述

### 1.1 项目背景
面向小学三年级学生的「暑假日常作业学习打卡」全周期管理系统，旨在通过数字化手段帮助学生养成每日打卡习惯，激励学习积极性，同时为家长和管理员提供便捷的监控与管理工具。

### 1.2 项目目标
- 实现学生每日作业打卡、补卡、审核的完整流程
- 建立积分激励体系（打卡赚积分、连续打卡解锁抽奖、积分兑换奖品）
- 提供家长绑定、实时通知、代为操作等家庭协作功能
- 构建管理员后台，支持打卡审核、奖品管理、数据统计
- 支持多平台消息推送（钉钉、企业微信）
- 确保系统安全、稳定、易部署、易维护

### 1.3 技术架构
- **后端**：FastAPI + SQLAlchemy 2.0 + SQLite
- **前端**：Vue 3 CDN（免构建）
- **部署**：Docker + docker-compose + Nginx 反向代理
- **安全**：bcrypt 密码哈希 + HMAC 签名 Token + 速率限制 + SSRF 防护
- **人脸识别**：insightface（buffalo_l）1:1 本人比对（支持降级安全模式）

## 三、技术实现亮点

### 3.1 架构设计亮点

#### 3.1.1 单后端多端托管
FastAPI 同时托管学生端H5、管理后台、上传资源三个静态目录，前端全部使用 Vue 3 CDN 版本免构建，降低部署复杂度。

#### 3.1.2 子路径部署自适应
前端 `BASE_PATH` 自动检测 `/homework` 前缀，动态推导所有API请求与资源URL，同一份代码既能在根路径运行，也能在Nginx反向代理下运行。

#### 3.1.3 分层清晰的后端架构
```
routers/    → 协议层（仅参数与鉴权）
services/   → 业务层（可测、无HTTP依赖）
utils/      → 工具层（通用工具函数）
```
业务逻辑不散落在路由中，复用优先（如群内审核复用 `checkin_service.approve/reject`）。

#### 3.1.4 单行配置表模式
`PushConfig`、`SiteConfig` 均采用「单行表 + get_or_create 惰性建行 + PUT 全量保存」，后台配置即改即生效，无需重启。

### 3.2 安全机制亮点

#### 3.2.1 防代打卡四重校验
1. **照片真实性**：合法JPEG/PNG、体积≥5KB、最小边长≥200px
2. **地理位置一致性**：Haversine距离超过1500m置 `geo_flag`
3. **人脸1:1本人比对**：insightface提取512维特征，余弦相似度低于0.4拒绝打卡（enforce模式）
4. **场景综合判定**：汇总为 `scene_check`（pass/warn/pending）

#### 3.2.2 回调验签与防重放
- **钉钉**：加签模式 `HMAC-SHA256(timestamp+"\n"+token)`，时间戳有效期1小时
- **企微**：AES-256-CBC加解密 + SHA1字典序验签 + msgid LRU排重（容量512）

#### 3.2.3 SSRF防护
Webhook URL仅允许钉钉/企微官方API前缀，其余一律拒绝保存。

#### 3.2.4 日志脱敏
PushLog不记录Webhook URL与Token，部署脚本输出对密码打码。

### 3.3 性能优化亮点

#### 3.3.1 推送异步化
Webhook推送在daemon线程执行，独立DB会话，任何异常只写PushLog，保证打卡主流程零阻塞。

#### 3.3.2 冗余统计字段
`User` 表内置 `current_streak / longest_streak / effective_checkins / lottery_tickets / points` 等冗余字段，每次有效打卡后重算落库，读取时零计算。

#### 3.3.3 静态资源缓存策略
静态资源版本号（`?v=YYYYMMDD`）强制客户端缓存刷新，配置接口 `cache:"no-store"` 保证实时生效。

### 3.4 时区治理亮点

#### 3.4.1 全链路naive北京时间
- 存储层统一使用 `utils/timeutil.now_local()` 显式+8，不依赖容器TZ
- Dockerfile设 `TZ=Asia/Shanghai` 覆盖 `date.today()` 类调用
- 统一naive避免offset-naive/aware混比错误

#### 3.4.2 历史数据迁移
迁移003对11张表时间戳整体+8h平移并重算 `check_date`，升降级双向可逆，生产13条打卡零丢失。

### 3.5 部署运维亮点

#### 3.5.1 双环境增量部署脚本
`scripts/deploy.sh local|prod`：部署前自动备份数据库 → 重建镜像（保留数据卷）→ 启动自动执行Alembic迁移 → 健康检查。

#### 3.5.2 数据持久化
数据库与上传目录通过环境变量重定向到命名卷（`summer-data`、`points-data`），跨容器重建数据不丢失。

#### 3.5.3 容器安全加固
`read_only: true`、非特权用户 `appuser`、`tmpfs /tmp`、最小权限原则。

## 四、遇到的问题及解决方案

### 4.1 时区偏差问题
**问题描述**：服务器时间显示为UTC，导致早上8点前打卡被记到前一天，前端时间显示差8小时。

**根因分析**：三层问题叠加——宿主机时钟正常、容器TZ=UTC、应用显式存UTC。

**解决方案**：
1. 容器加 `TZ=Asia/Shanghai`
2. 应用层新建 `timeutil.now_local()` 统一替换22处写库点
3. 历史数据用迁移003整体平移+8h
4. 生产13条打卡零丢失

### 4.2 人脸识别沙箱降级问题
**问题描述**：无外网环境无法下载insightface模型，导致人脸比对功能不可用。

**解决方案**：
- 启动时探测模型可用性，不可用自动降级安全模式
- 已采集底图的账号打卡被拒绝（防绕过），未采集账号正常
- 采集/比对/拦截链路完整可演示
- 部署环境联网即自动生效

### 4.3 推送故障影响主流程风险
**问题描述**：Webhook推送若同步执行，外部网络异常会阻塞打卡主流程。

**解决方案**：
- daemon线程异步执行 + 独立DB会话
- 任何异常只写PushLog，绝不影响打卡主链路
- 推送日志脱敏，不记录URL与Token

### 4.4 敏感信息泄露风险
**问题描述**：早期版本存在明文账号密码入库、密钥文件未忽略等安全隐患。

**解决方案**：
- 全库敏感信息清理
- 根 `.gitignore` 门禁体系（密钥/数据库/上传/备份/日志全类目拦截）
- 提交前逐文件扫描 + 安全扫描门禁
- 改用环境变量与随机生成机制

### 4.5 部署脚本健康检查误报
**问题描述**：迁移+启动实际约15s，超过脚本10s阈值，导致误报部署失败。

**解决方案**：
- 建立「脚本报错 → 人工复核容器状态/迁移日志/health」的标准复核流程
- 调整健康检查等待时间

### 4.6 企微双向消息协议适配
**问题描述**：企微「智能机器人」回调协议与钉钉Outgoing协议差异大，需要AES加解密+SHA1验签+msgid排重。

**解决方案**：
- 实现 `utils/wecom_crypto.py` AES-256-CBC加解密工具
- 被动回复采用stream类型一次性应答
- msgid LRU排重（容量512）防网络重试重复执行
- 指令集与钉钉完全一致，复用 `handle_command` 逻辑
